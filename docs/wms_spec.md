# Дизайн-спека: WMS Market Partners — фаза 1 (MVP)

**Контекст:** фулфилмент в Чехове (МО), 2–3 клиента, 200–1500 FBS-заказов/день (WB/Ozon), партионный учёт со сроками годности, прогрессивное хранение (30 дней бесплатно, дальше по возрасту партии), клиентам обещан ЛК с остатками онлайн.

**Стек (рекомендация, совместимо с текущей практикой команды):** FastAPI + Postgres + vanilla JS (мобильный веб вместо нативного ТСД-приложения — Отчёт 3: «телефон + камера/BT-сканер достаточно, персонал без обучения»). ТСД = Android-смартфон (практика МПФИТ, Отчёт 1, п.7 «что взять»).

**Три несущих принципа (из всех четырёх отчётов, нарушать нельзя):**
1. **Остаток = свёртка append-only журнала операций**, не редактируемое поле (Отчёт 3, «что ломается первым в самописных WMS», п.1–2).
2. **Каждая операция сразу порождает billing_event** — счёт в конце месяца это агрегация, а не пересчёт (Отчёты 1/2/4: OrderAdmin real-time billing, Extensiv Billing Wizard).
3. **Мультиарендность с первой таблицы**: `client_id` в каждой сущности, жёсткая изоляция (Отчёт 1, грабля №6: МойСклад/СКИФ ломаются на «клиенты как склады»).

## 1. Экраны

### 1.1. Сотрудник склада (мобильный веб, телефон/ТСД)

Общие правила UI (Отчёт 3, раздел 1): скан — основной ввод; экран показывает одно действие («что сканировать дальше и сколько»); зелёный/бип = ок, красный/другой звук + вибро = ошибка; сканер программно отключается на полях ручного ввода; крупные touch-цели; валидация до подтверждения.

Вердикт — справочник, не free-text |

## 2. Схема данных

Каждая таблица с товарным/денежным смыслом несёт `client_id`. Все операционные таблицы append-only; правки — только сторно.

**Справочники и мастер-данные**

- `client` — id, name, inn, settings_json (регламент возвратов, пороги уведомлений), telegram_chat_id.
- `user` — id, role (admin / warehouse / dispatcher / client_user), client_id (null для сотрудников склада).
- `sku` — id, client_id, code, name, photo_url, volume_l, weight_g, dims (ВГХ фиксируются при приёмке обмером — защита от спора «неверные ВГХ», Отчёт 4), requires_expiry bool, shelf_life_min_days (FEFO-порог отгрузки).
- `barcode` — id, sku_id, barcode, source (wb / ozon / supplier / internal). **Many-to-one: без этой таблицы скан не работает вообще** (Отчёт 3, грабля №5).
- `location` — id, zone (storage / pick / quarantine / returns / outbound), rack, shelf, code (скан-код), volume_l.
- `license_plate` — id, code, location_id (паллета/короб как один сканируемый объект).

**Партии и остатки**

- `batch` — id, client_id, sku_id, batch_no, expiry_date, **received_at** (= дата завершения приёмки; кормит и FEFO, и возрастной биллинг — одна сущность на обе фичи, Отчёт 1, бонус), inbound_id.
- `stock_move` — **ядро системы, append-only журнал**: id, client_id, sku_id, batch_id, qty (+/–), from_location_id, to_location_id, stock_status (available / reserved / quarantine / damaged), doc_type + doc_id (inbound / order / return / adjustment / writeoff), user_id, created_at, reversal_of_id. Остаток любой размерности = `SUM(qty)` по срезу. Прямых UPDATE остатков не существует как класса (Отчёт 3, грабли №1–2, №6).
- `stock_snapshot` — ежедневный ночной срез: date, client_id, sku_id, batch_id, location_zone, qty, volume_l, age_days. Источник биллинга хранения и ответ на «в середине месяца у меня было меньше» (Отчёт 3, грабля №3).

**Приёмка**

- `inbound` (ASN) — id, client_id, status (draft / expected / receiving / received / closed), expected_date, created_by_client bool.
- `inbound_line` — inbound_id, sku_id, qty_expected, qty_received, batch_no_declared, expiry_declared.
- `inbound_discrepancy` — inbound_line_id, type (short / over / damaged / wrong_sku — enum, не текст), qty, photo_ids[], client_confirmation (pending / accepted / disputed), deadline_at (срок подтверждения клиентом).
- `photo` — id, doc_type, doc_id, url, taken_at, user_id (единая таблица фотофиксации: приёмка, возвраты, отгрузка).

**Заказы FBS**

- `order` — id, client_id, marketplace (wb / ozon), mp_order_id, status (new / allocated / picking / packing / packed / shipped / cancelled / exception), exception_reason (enum: out_of_stock / not_found_in_bin / damaged_on_pick / label_fail), cutoff_at, wave_id, raw_json.
- `order_line` — order_id, sku_id, qty, allocated_batch_id (назначается FEFO при резерве).
- `reservation` — order_line_id, batch_id, qty, created_at. **Создаётся атомарно в транзакции приёма заказа по API** — иначе двойная продажа WB+Ozon (Отчёт 3, грабля №4).
- `wave` — id, marketplace, cutoff_at, courier ("WB Чехов 16:00"), status.
- `pick_batch` — id, wave_id, picker_id, cart_slots (заказ → ячейка тележки), status.
- `outbound_box` — id, wave_id, direction, label_scans[] (контроль «всё собранное уехало в правильную машину»).

**Возвраты**

- `return` — id, client_id, marketplace, mp_return_id, order_id?, status (arrived / inspecting / resolved), verdict (to_stock / damaged / dispose / to_client — enum), photos_before[], photos_after[], resolved_by, resulting stock_move id.

**Пересчёты**

- `cycle_count` — id, location_id, trigger (zero_on_pick / pick_shortage / return_placed / manual), counted_qty (слепой ввод), system_qty (фиксируется после ввода), user_id.
- `adjustment` — cycle_count_id?, client_id, sku_id, batch_id, qty_delta, reason (enum), approved_by → порождает stock_move; клиент видит в ЛК (Отчёт 2 №13).

**Биллинг (по спеке Отчёта 4, §5.1 — берём как есть)**

- `rate_card` — id, client_id, valid_from, valid_to, status (draft / active / archived); версии неизменяемы после активации.
- `rate_line` — rate_card_id, service_code (RECEIVE_BOX, RECEIVE_UNIT, PUTAWAY, PICK_ORDER_FIRST, PICK_ITEM_ADD, PACK_BAG, PACK_BOX, STICKER_WB, STICKER_OZON, STORAGE_DAY, RETURN_PROCESS, VAS_*…), unit, price, formula_note.
  - Паттерн «первый item + доп. item» в сборке — защита от мультитоварных заказов (Отчёт 4 §1.1).
- `storage_age_band` — rate_card_id, age_from_days, age_to_days, coefficient (**0 для 0–30**), min_per_unit (MAX-защита а-ля Amazon от мелкого многоштучного товара).
- `billing_event` — **append-only**: id, client_id, service_code, qty, rate_line_id + **snapshot цены**, amount, occurred_at, source_type/source_id, sku_id, batch_id, operator_id, meta json (формула с числами), reversal_of_id.
- `client_ledger` — проводки (top-up / charge / reversal), баланс = сумма; block_level (0 нет / 1 warn / 2 блок отгрузок / 3 полный блок).
- `invoice` — period, client_id, status (draft / sent / paid / disputed), строки = агрегаты по service_code со ссылкой на выборку billing_event. Инвариант закрытия: Σ billing_event = Σ строк инвойса, иначе акт не выпускается.

## 3. Потоки

### 3.1. Приёмка
1. Клиент создаёт ASN в ЛК (К2): SKU, кол-во, партии/сроки, тара. Товар без ASN не принимается — исключение только через диспетчера с логом.
2. Машина пришла: фото паллет ДО вскрытия при видимых повреждениях.
3. Кладовщик (С1): скан ШК → матч через `barcode` → факт-кол-во → **обязательный ввод expiry + batch_no** (форма не пропускает) → расхождения кнопкой + фото. Нет ШК у товара → печать внутренней этикетки на месте (Отчёт 1, грабля №7).
4. Завершение приёмки: создаются `batch` (received_at = сейчас → старт 30 бесплатных дней), `stock_move` (+qty → зона приёмки), `billing_event` (RECEIVE_*), акт расхождений уходит клиенту в ЛК + Telegram с дедлайном подтверждения.
5. Putaway (С2): скан LP → предложенная ячейка → скан ячейки → `stock_move` в storage, `billing_event` (PUTAWAY).
Метрика: dock-to-stock time (пишется из timestamps журнала).

### 3.2. Хранение
- Ночной cron: `stock_snapshot` по каждой партии (qty × volume_l × age_days).
- Из снапшота — `billing_event` STORAGE_DAY: `volume × ставка × coefficient(band(age))`, с min_per_unit-защитой; **0–30 дней = коэффициент 0**; начисление **прекращается в день фактической отгрузки партии** (частейший источник споров, Отчёт 4 §5.4).
- ЛК К4 показывает возраст, дни до платности, прогноз. Уведомление за 3 дня до перехода партии в платную/следующую корзину.

### 3.3. Сборка FBS
1. Поллинг API WB/Ozon → `order` + **атомарный резерв** `reservation` по FEFO (батч с ближайшим expiry, но не ниже shelf_life_min_days). Нет остатка → status=exception (out_of_stock), клиент видит в К3.
2. Диспетчер (С8): заказы падают в волны по cutoff; формирует пик-батчи 10–30 заказов, single-SKU-заказы — отдельными батчами (Отчёт 2 №6).
3. Пикер (С3): скан ячейки → скан товара → следующая строка; FEFO-партию диктует система. «Не хватило» → exception + авто-задание `cycle_count` на ячейку.
4. Упаковщик (С4): scan-to-pack, этикетка МП печатается после полной сверки, сразу клеится. `billing_event`: PICK_ORDER_FIRST + PICK_ITEM_ADD×(n−1) + PACK_* + STICKER_*.
5. Резерв закрывается фактическим `stock_move` (−qty) при упаковке.

### 3.4. Отгрузка
- Скан этикетки заказа при укладке в `outbound_box` направления → контроль полноты волны.
- С5: закрытие волны, фото передачи, статус shipped → в ЛК и по API-статусам. SLA-метрика «% собрано до cutoff» пишется автоматически из журнала.

### 3.5. Возврат
- Приём возврата сканом → `return` → фото ДО вскрытия → инспекция → вердикт по регламенту клиента → фото ПОСЛЕ.
- to_stock: проверка остаточного срока (FEFO-порог) — просрочка/короткий срок автоматически не возвращается в available; `stock_move` в storage со **старой партией** (received_at не сбрасывается — возраст для биллинга честный).
- damaged/dispose: `stock_move` в зону quarantine/списание; в К1 — отдельная колонка, никогда не смешивается с available.
- `billing_event` RETURN_PROCESS (+VAS переупаковки) — возвраты это доход оператора (Отчёт 3).

### 3.6. Биллинг
- Каждая операция потоков выше уже породила `billing_event` в момент скана — клиент видит ленту накопительно каждый день (К5).
- Нетарифицированное событие (операция без rate_line) → очередь диспетчеру, не молчаливый ноль.
- Конец месяца: генерация invoice + XLSX-детализация (сводка / операции / хранение по дням-партиям); инвариант Σ событий = Σ инвойса.
- Баланс: предоплатная модель (РФ-норма). Автостоп **ступенчатый**: баланс < порога → уведомление; ≤ 0 → блок новых FBS-отгрузок (приёмка и просмотр остатков работают); долг > N дней → полный блок кроме выдачи товара. **Хранение продолжает начисляться при блоке.** Заблокированные заказы видны клиенту со статусом «ожидает оплаты», не исчезают.
- Смена тарифа = новая версия rate_card с датой + уведомление за 14 дней; цена в событии всегда из версии, действовавшей в occurred_at.

## 4. Что сознательно НЕ делаем в MVP

| Не делаем | Почему |
|---|---|
| Автомаршрутизация обхода и волновая оптимизация | До ~500 зак/день хватает ручных батчей, сортированных по коду ячейки (Отчёт 3) |
| Конструктор тарифов «на всё» в UI | Главная жалоба на МПФИТ — «день на настройку и не смог». Rate card v1 = фиксированный набор service_code, правится админом; конструктор — при 5+ клиентах |
| ABC-планировщик циклических пересчётов | Триггерных пересчётов достаточно; ABC — при 5+ клиентах |
| Автосоздание поставок/слотов WB-Ozon по API | Диспетчер делает руками в кабинетах МП; API-методы WB нестабильны (см. опыт проекта: методы умирают) |
| Споры (dispute) как workflow в ЛК | При 2–3 клиентах решается в мессенджере; **акты и фото уже есть** — схема данных готова, UI позже |
| KPI-дашборды, зарплата кладовщиков (сдельная) | Данные уже в журнале операций — отчёты дорисовываются, когда будет с чем сравнивать (та же лента событий даёт выработку «почти бесплатно», Отчёт 1 №9) |
| Офлайн-режим ТСД | Wi-Fi на малом складе стабилен |
| White-label / API для клиентов / интеграция с 1С клиентов | По первому реальному запросу |
| «Честный знак», видеофиксация сборки | Вторая очередь; фотофиксация в MVP закрывает 80% доказательной ценности |
| Авто-акты/УПД, объёмные tiers, split-period storage | Ручной акт из XLSX-детализации при 2–3 клиентах ок; инвариант Σ=Σ уже соблюдается |
| Нативное Android-приложение ТСД | Мобильный веб + BT/камера-сканер; нативное — если упрёмся в скорость скана |

**Но закладываем в схему сразу** (дописать потом почти невозможно): client_id везде, batch как first-class сущность, append-only журнал, billing_event, снапшоты, enum-справочники причин, таблица barcode many-to-one, reversal_of_id.

## 5. Топ-10 граблей, от которых спека защищает

1. **Остатки расходятся с реальностью** → остаток только как свёртка append-only `stock_move`; правки только сторно-документом с причиной; админского UPDATE не существует.
2. **Спорный биллинг хранения** («в середине месяца было меньше») → ежедневный `stock_snapshot` по партиям; каждая строка счёта кликабельна до операции; начисление останавливается в день отгрузки партии.
3. **Двойная продажа WB+Ozon** → атомарный резерв в транзакции приёма заказа по API; Available/Reserved раздельно везде, включая ЛК.
4. **Переклейка этикеток / мис-шип → штрафы МП** → scan-to-pack: этикетка печатается только после сверки сканом каждой позиции; печать пачкой заранее запрещена архитектурно (нет такой кнопки).
5. **«Мы отправили 100, вы приняли 96»** → приёмка только против ASN, расхождения — типизированные записи с фото в момент приёмки, подтверждение клиентом в ЛК с дедлайном.
6. **Потерянные сроки годности / нечестный возраст партии** → expiry + batch обязательны на приёмке (форма не пропускает); received_at партии кормит и FEFO, и биллинг — одна сущность, рассинхрон невозможен; возврат не сбрасывает возраст.
7. **Пересорт из-за зоопарка штрихкодов WB/Ozon/поставщика** → таблица `barcode` many-to-one с первого дня; товар без ШК получает внутреннюю этикетку на приёмке.
8. **Смешение годного, брака и резерва в одном числе** → stock_status в каждом движении; карантин/брак — отдельные зоны и отдельные колонки в ЛК.
9. **Клиенты «складами» без изоляции** → tenant = client_id в каждой таблице; права client_user жёстко ограничены своим client_id на уровне запросов.
10. **Порог входа и «система требует внедренца»** → фиксированный набор service_code вместо конструктора, справочники вместо free-text, смарт-дефолты, онбординг «завёл клиента → скопировал rate card от шаблона → загрузил SKU → работаешь» — целевое время до первой приёмки нового клиента: 1 час.

**Критерий готовности MVP:** один клиент проходит полный цикл ASN → приёмка с расхождением → хранение с переходом партии через 30 дней → 50 FBS-заказов батчем → отгрузка в волну → возврат с вердиктом → месячный акт, где Σ событий = Σ инвойса и каждая строка раскрывается до скана, — без единого ручного UPDATE в базе.
